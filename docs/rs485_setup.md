# Связь ноутбук <-> привод по Modbus RTU через USB-RS485

Пошагово, от «воткнул переходник» до «регистр читается».

## 0. Главная ловушка macOS

У одного физического адаптера в системе появляются **два** устройства:

```
/dev/tty.usbserial-XXXX    dial-in  — открытие может зависнуть навсегда
/dev/cu.usbserial-XXXX     call-out — открывать надо ЭТО
```

`tty.*` при открытии ждёт сигнал DCD, которого у RS-485-переходника нет.
Симптом — скрипт молча висит на `connect()`. Всегда берите `/dev/cu.*`.

## 1. Найти переходник

```bash
.venv/bin/python examples/ports.py
```

Скрипт показывает только call-out устройства с чипами FTDI, CH340, CP210x и
PL2303 — то есть отсеивает Bluetooth и системные порты.

Если пусто:

```bash
ioreg -p IOUSB -l -w 0 | grep -i "USB Product"
```

Устройство видно, а порта нет — не хватает драйвера (актуально для CH340 на
старых macOS, у FTDI и CP210x драйверы встроенные). Не видно вообще — кабель
или сам адаптер.

## 2. Провода

| Переходник | Привод |
|---|---|
| A (D+) | A (485+) |
| B (D-) | B (485-) |
| GND | GND сигнальный |

* **Витая пара** на A/B. Не разные жилы плоского шлейфа.
* **GND обязателен.** Без общей земли связь «почти работает»: короткие
  посылки проходят, длинные рассыпаются, всё пляшет от нагрузки на двигателе.
* Терминаторы 120 Ом на обоих концах сегмента. На коротком столе можно без,
  на машине — нужно.
* **A и B перепутать не страшно** — не сгорит, просто не будет связи.
  Не заработало с первого раза — поменяйте местами, это первое, что надо
  попробовать.

## 3. Параметры связи

Нужны четыре числа: скорость, чётность, стоп-биты и адрес ведомого. Они
задаются в самом приводе, смотрите его параметры связи с панели.

Не знаете — переберите:

```bash
.venv/bin/python examples/scan_bus.py /dev/cu.usbserial-XXXX --ids 1-32
```

Скрипт гоняет скорости 9600…115200 на всех чётностях и адресах и читает
`P-003` (версия ПО, только чтение — ничего не портит). Найденное печатает.

## 4. Проверить обмен

```bash
.venv/bin/python examples/mb.py read P-004
.venv/bin/python examples/mb.py read 40077
.venv/bin/python examples/mb.py read 0x1011
```

Адрес понимается в трёх видах: `P-004`, нотация `40077` (= 40001 + номер) и
сырой `0x1011`. Порт подхватывается сам, если переходник один.

Смотреть регистр в реальном времени, пока крутится вал:

```bash
.venv/bin/python examples/mb.py watch 0x1011 --count 2
```

## 5. Писать — только со сверкой

```bash
.venv/bin/python examples/mb.py write P-076 100 --verify
```

`--verify` читает значение обратно. Это не паранойя: у привода есть пароль
`P-000` (по умолчанию 315; для `P-001`/`P-002`/`P-099` нужен 385 или 316), и
**без него запись проходит молча, а значение не меняется**. Modbus отвечает
«ок», Python радуется, привод игнорирует. Без сверки такое ищется часами.

## 6. Из своего скрипта

```python
from scara_drive import DriveConfig, SerialConfig, ServoDrive

cfg = DriveConfig(serial=SerialConfig(
    port="/dev/cu.usbserial-XXXX", baudrate=19200, parity="N", device_id=1,
))

with ServoDrive(cfg) as drive:
    drive.write_param(76, 100)          # P-076
    assert drive.read_param(76) == 100  # сверка обязательна
    drive.run(speed=100)
```

Через шлюз Ethernet<->RS-485 меняется одна строка:

```python
from scara_drive import TcpConfig
cfg = DriveConfig(tcp=TcpConfig(host="192.168.1.50", device_id=1))
```

## Если не отвечает

По порядку, от частого к редкому:

1. Взяли `/dev/tty.*` вместо `/dev/cu.*`.
2. Перепутаны A и B — поменяйте местами.
3. Не подключён GND.
4. Не тот адрес ведомого или скорость — `scan_bus.py`.
5. Не та чётность. `8N1` и `8E1` встречаются одинаково часто.
6. Порт занят другой программой — второй питон, монитор порта, Arduino IDE.
7. Привод не в том режиме: у части приводов управление по RS-485 надо
   разрешить отдельным параметром, иначе он слушает только клеммник.
8. Адаптер без автоматического переключения приёма/передачи. Дешёвые платы на
   MAX485 требуют управления DE/RE; годятся только те, где это сделано
   аппаратно. У переходников на CH340+MAX485 обычно уже так.
